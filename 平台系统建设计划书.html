一、背景与建设目标

平台已完成低代码大屏设计器（画布编辑 / 组件拖拽 / 预览发布）、大屏管理列表、36 条基础路由功能页与 NestJS 后端骨架（项目 / 大屏 / 运行时 / 数据服务 / 生态 / 实时 / 资产 / 审计 / 通用目录九大服务模块）。前端请求适配层 mockFetch 已直通真实后端，统一 {code, data, message} 信封。

本期目标：将平台从「大屏工具」升级为「企业级平台系统」——补齐七大核心模块的功能闭环，且所有模块产出均可被大屏管理系统以标准化开放接口（能力注册表 GET /api/open/capabilities）统一引用与编排。

  • 闭环完整：每个模块具备「创建 → 管理 → 消费 → 监控」全生命周期能力，不留只读死角。
  • 标准引用：七大模块的资源以统一资源描述符对外暴露，设计器 / 编排引擎按同一协议消费。
  • 前后端同构：后端 NestJS 模块化落库（Prisma），前端功能页真实接口驱动，无孤儿 mock。
  • 可扩展高可用：微内核 + 插件化 + 通用资源目录（kind 驱动），新增领域零迁移成本。

五、七大模块详细设计

5.1 组件中心模块

需求描述（EARS）

Ubiquitous：系统应始终维护每个组件的唯一标识、当前版本号与生命周期状态。
Event-driven：当管理员发布组件新版本时，系统应生成不可变版本记录（版本号 + 变更日志 + 时间戳）并更新当前版本指针。
State-driven：当组件处于 deprecated / offline 状态时，设计器物料面板不应再提供该组件的新增拖入。
Unwanted：若删除被大屏引用的组件定义，系统应拒绝并返回引用清单。

接口设计

接口说明
GET/POST/PATCH/DELETE /api/widgets(/:id)组件定义全量 CRUD（检索 / 分类 / 分页）
GET /api/widgets/:id/versions · POST /api/widgets/:id/versions版本链查询 / 发布新版本 {version, changelog}
POST /api/widgets/:id/lifecycle生命周期流转 {status: draft|published|deprecated|offline}
GET /api/widgets/stats状态监控：按状态 / 分类计数

5.2 AI 智能模块

Event-driven：当调用方提交时间序列与步长时，系统应返回等长预测序列及置信区间。
Where：在设计器请求推荐时，系统应结合场景关键词返回推荐组件清单与布局建议。
接口说明
POST /api/ai/predict数据预测：{series, steps} → {forecast, trend, confidence}（线性回归 + 移动平均）
POST /api/ai/recommend智能推荐：{scene, dataShape?} → {widgets[], layout, reason}
POST /api/ai/analyze智能分析：{data} → {insights[]}（极值 / 趋势 / 波动 / 异常点洞察）
POST /api/ai/chat · POST /api/ai/generate已有：自然语言交互 / 代码生成（预留真实 LLM 接入位）

If 未配置真实大模型密钥，then 系统应以内置规则引擎离线降级，接口契约不变。

六、标准化开放接口契约（大屏系统统一引用）

所有模块产出通过能力注册表对大屏管理系统暴露，实现「一个入口、统一协议、可编排」：

GET /api/open/capabilities
→ {
  "code": 0,
  "data": {
    "version": "1.0",
    "envelope": { "code": "number(0=成功)", "data": "T", "message": "string" },
    "modules": [
      {
        "key": "component-hub", "name": "组件中心",
        "resources": [
          { "kind": "widget", "name": "可视化组件", "basePath": "/api/widgets",
            "ops": ["list","get","create","patch","delete"],
            "actions": ["versions","lifecycle","stats"],
            "count": 12, "consumableBy": ["designer.material","dashboard.orchestrate"] }
        ]
      },
      { "key": "ai", ... }, { "key": "devtools", ... }, { "key": "resource", ... },
      { "key": "system", ... }, { "key": "plugin", ... }, { "key": "infra", ... }
    ]
  }, "message": "ok"
}
  • 资源描述符五要素：kind（类型）、basePath（入口）、ops（标准 CRUD 能力）、actions（行为动作）、consumableBy（可被哪些编排点消费）。
  • 大屏设计器「能力映射」面板由静态 capabilities.ts 升级为实时拉取本注册表，动态感知后端能力与资源数量。
  • 统一信封 {code, data, message}、统一分页 {list, total, page, pageSize}，任何新模块按此协议接入即被自动编排。

七、模块间数据流转闭环

组件中心(widget/版本) ─┐ 资源管理(素材/地图) ─┤ ┌─▶ 大屏发布(Screen 版本快照) AI 智能(推荐/预测) ─┼─▶ 能力注册表 ─▶ 设计器画布 ─┤ 开发工具(变量/代码) ─┤ open/capabilities └─▶ 运行时 runtime(缓存读取) 插件管理(扩展组件) ─┘ │ ▼ 系统管理(权限/参数) ──守卫全链路 审计日志 ◀── 全部写操作 基础支撑：调度任务──▶数据同步──▶数据源/数据集──▶画布组件绑定 告警规则──超阈值──▶通知中心──▶前端消息中心/WS 推送

闭环要点：任一模块的「产出」（组件、素材、模型、变量、插件）都经能力注册表进入设计器消费；任一「运行事件」（调度、同步、告警）都回流通知中心与审计日志，形成生产 → 消费 → 监控 → 反馈的完整回路。

八、可扩展性与高可用设计

可扩展性

  • 微内核 + kind 驱动：通用 Resource 表承载元数据型领域，新增领域 = 新增 kind + 路由登记，零迁移。
  • Connector 注册表：数据源类型（static / http-api / sql / mqtt）按接口注册可插拔。
  • 插件状态机：第三方组件 / 数据源 / 动作经审核后热接入物料体系。
  • 前后端契约先行：信封 + 分页 + 资源描述符三协议固定，双端独立演进。

高可用

  • 存储分级：开发 SQLite 零配置，生产切 PostgreSQL 仅改 DATABASE_URL。
  • 缓存分级：运行时读取走内存缓存，生产可无缝切 Redis。
  • 发布快照：大屏发布生成不可变版本，支持秒级回滚。
  • 容器化：已备 Dockerfile / docker-compose，可水平扩展多实例 + 前置负载均衡。
  • 降级策略：AI 无外部模型时规则引擎降级；后端不可达时前端信封返回 code=-1 可控提示。

九、里程碑与验收标准

阶段交付物验收标准
M1 计划评审本计划书七模块范围 / 契约确认
M2 后端补齐platform 模块（组件版本 / AI / 开发工具 / 系统 / 插件运维 / 调度同步通知 / 能力注册表）NestJS 构建通过；新接口 curl 冒烟全绿
M3 前端接入api 门面增补 + 组件中心版本操作 + 调度 / 同步 / 通知 / 监控新页 + 能力映射实时化tsc --noEmit 0 错误；vite build 成功
M4 联调验收前后端联调记录七模块页面均可对真实后端完成读写闭环

总验收口径：① 每个模块至少一条「创建→消费→监控」链路可演示；② GET /api/open/capabilities 覆盖全部七模块资源；③ 前端零 TypeScript 错误、后端零构建错误。
