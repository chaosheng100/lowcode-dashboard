# 2026-07-30 工作日志

## 修复：大屏管理「新增/预览/编辑」打不开（HashRouter URL 错误 + 鉴权拦截）

### 现象
大屏管理页（`ScreenListPage`，`?screens=list`）能正常展示，但点「编辑」「预览」会弹出一个窗口却显示错误页面（登录页或主应用路由树），点「新建」后也无法进入编辑器。

### 根因（两处叠加）
1. **HashRouter URL 写错**：应用用 `HashRouter`，参数必须放在 `location.hash` 内（`#/?mode=...`）。
   - `ScreenListPage.openEditor/openPreview` 原来拼的是 `?mode=editor&routeId=...`（非 hash），新窗口的 `useLocation().search` 为空 → 读不到参数 → 进不了编辑器。
   - `designer/window.ts` 的 `openEditorWindow/openPreviewWindow` 用 `new URL(location.href).searchParams.set(...)`，也是把参数写进 search 而非 hash，同样打不开（影响 ProjectView 的本地编辑/预览）。
2. **鉴权拦截**：`App.tsx` 里 `RemoteWindowApp`（后端持久化）排在 `if (!token) return <LoginPage/>` 之后；但后端 `/api/screens/*` 无需鉴权，且 `ScreenListPage` 已绕过鉴权 → 未登录用户点编辑/预览会进登录页。

### 修改文件
- `src/App.tsx`
  - `remote=true` 的 editor/preview 窗口提前 `return <RemoteWindowApp/>`，绕过登录态（与 ScreenListPage 一致，匹配后端无鉴权设计）。
  - 模块级 `isRemote` 判定改为从 `location.hash` 解析（`initPersist` 在 HashRouter 下 `location.search` 永远为空，导致 remote 窗口也初始化了本地持久化、污染本地 store）。
- `src/api/ScreenListPage.tsx`
  - 新增 `buildRemoteUrl()`：拼 `#/?mode=...&routeId=...&remote=true` 的 hash URL。
  - `openEditor/openPreview` 改用该 hash URL。
  - `handleCreate` 创建成功后直接 `openEditor(newId)` 打开编辑器（在用户手势内调用 window.open，避免被拦截）。
- `src/designer/window.ts`
  - `buildWindowUrl()` 改为拼 hash URL（`#/?mode=...&routeId=...`），修复 ProjectView 本地编辑/预览打不开。

### 验证
- `npx tsc --noEmit` → exit 0。
- `npx vite build` → exit 0。
- node 模拟解析：`#/?mode=editor&routeId=abc&remote=true` 能被正确解析出 `mode/routeId/remote`（即 App 能正确进入 RemoteWindowApp）。
- 后端 create/detail/save/delete 此前已实测返回 `code:0`（无需鉴权）。

### 注意
- HashRouter 是整个项目 URL 参数的「隐含约定」：**任何 `window.open` 跳转本应用页签、且需携带 mode/routeId 等参数时，都必须写进 hash 查询串**，否则新页签读不到参数。本次已统一两处。

## 修复（续）：「新建大屏」仍不行 —— prompt 被沙箱禁用 + 后端宕机

### 现象
上一轮改完 hash URL 后，用户反馈「新建大屏还是不行」。

### 根因（两处）
1. **`window.prompt` / `window.alert` 在沙箱/预览环境被禁用**：`handleCreate` 用 `window.prompt` 取名称，被禁用后直接返回空 → 函数提前 return，什么都没发生；错误分支的 `alert` 同样不显示。且创建成功后的 `window.open` 写在 `await` 之后，易被浏览器弹窗拦截器拦截。
2. **后端进程宕机**：排查时发现 `http://localhost:3000/api/screens` 返回 HTTP=000（连接被拒），`apps/api/dist/src/main.js` 也不存在（之前进程应是崩溃/被清理）。前端大屏管理整条链路（list/create/editor 加载）都依赖该后端，宕机时新建当然失败。

### 修改
- `src/api/ScreenListPage.tsx`
  - 用 antd `Modal` + `Input` 替代 `window.prompt` 取大屏名称（沙箱安全）。
  - 新建流程改为：在「创建并打开编辑器」按钮的**点击手势内**先 `window.open('', '_blank', ...)` 拿到窗口句柄（避免被弹窗拦截），再 `await create`，成功后用 `win.location.href = buildRemoteUrl('editor', id)` 跳转编辑器；兜底若句柄为空再 `window.open`。
  - `alert(...)` 全部改为 `App.useApp()` 的 `message.success/error/warning`（沙箱安全）。
- 重启后端：`cd H:/Project/code/lowcode-dashboard-server/apps/api` → `node_modules/.bin/tsc -p tsconfig.json` → `node dist/src/main.js`（Prisma client 已生成，无需 regenerate）。重启后 `/api/screens` 恢复 HTTP=200，create 返回有效 `id`。

### 验证
- `npx tsc --noEmit` → exit 0；`npx vite build` → exit 0。
- 后端 create 实测返回 `code:0` 且含 `id`（如 `f06ea3d8-...`），编辑器 hash URL 可正确拼出。

### 运维提示（重要）
- 后端 `lowcode-dashboard-server` 会**自行崩溃**（本次发现 dist 缺失 + 端口无监听），前端大屏管理依赖它。每次报「大屏管理 xxx 不行」先 `curl -s -m5 -o /dev/null -w "%{http_code}" http://localhost:3000/api/screens` 确认后端在线；离线就按上面命令重启。
- 前端若通过 IDE 内嵌预览/iframe 打开，`window.prompt`/`window.alert` 不可用，必须用 Modal/message。

## 修复（续）：UserMenu.tsx:76 崩溃（user.roles 为 undefined）

### 现象
`UserMenu` 在 `ProjectView`（默认落地页）渲染时崩溃：`Cannot read properties of undefined (reading 'map')` @ `UserMenu.tsx:76`（`user.roles.map`）。

### 根因（两层）
1. **后端 login 响应剥掉了 roles**：`auth.service.ts` 的 `login()` 返回 `user: this.toSafeUser(user)`，而 `toSafeUser()` 只返回 `id/email/name/status/orgId`，**不含 `roles`/`permissions`**。但 `profile()` 用的是完整映射（含 roles）。所以登录后前端存进 localStorage 的 user 没有 `roles` → `UserMenu` 渲染时 `user.roles` 为 undefined → `.map` 崩溃。
2. **前端无兜底**：`UserMenu` 直接 `user.roles.map`，未做空值守卫（与之前 ReportManagement 同类问题）。

### 修改
- 后端 `apps/api/src/auth/auth.service.ts`
  - 新增私有方法 `toFullUser(user)`：返回含 `roles`（code+name）与 `permissions` 的完整用户对象（逻辑与 `profile()` 一致，从 `user.roles` 展开权限）。
  - `login()` 改用 `this.toFullUser(user)`（原来是 `toSafeUser`，剥字段）。
  - `profile()` 改用 `this.toFullUser(user)`（消除重复映射）。
  - `register()` 仍用 `toSafeUser`（注册后通常跳转登录，不存为当前用户）。
- 前端 `src/auth/UserMenu.tsx`：`{(user.roles || []).map(...)}` 兜底，避免任何缺字段的记录再崩。

### 验证
- 后端重新 `tsc` 构建并重启（`/api/screens` 恢复 HTTP=200）。
- 实测 register + login：login 响应现在含 `"roles":[]`（新用户无角色，空数组，不再缺失字段）→ 修复确认。
- 前端 `npx tsc --noEmit` → exit 0。
- 测试用户已清理。

### 注意
- 后端 `tsc -p tsconfig.json` 当前对 `src/agent/component-catalog.service.ts` 报 2 个**类型错误**（TS7053 索引、`TS2339` ComponentDef 缺 scope/ownerId），属既有问题、与本次无关。因 tsconfig 未设 `noEmitOnError`，tsc 仍会 emit 运行时 JS，后端可正常运行；改动 auth 模块不影响这些既有错误。
- 同类「直接读后端返回数组字段、无兜底」的页面还有多个（数据集/数据源/用户管理等），之前已提示过批量审计。

## 修复（续）：右上角被 UserMenu（角色信息浮层）遮挡

### 现象
默认落地页 `ProjectView`（`RoutePanel` + 内容区）右上角被「用户/角色信息」浮层遮住，导致大屏管理等页工具条右侧的「搜索 / 排序 / 新建大屏」等操作被盖住、点不到。

### 根因
`UserMenu` 在 `ProjectView` 中以 `position:absolute; top:12; right:16; zIndex:50` 浮在内容区之上；而默认视图是「大屏管理页」（`DashboardManagement`），其工具条 `.mg-toolbar` 右侧操作区仅离右边缘 `24px`（`.mg-title` 之外用 `margin-left:auto` 把搜索框/排序/新建按钮顶到最右）。浮层宽度约 150px，正好盖住这些按钮。同理功能页头 `.oa-head` 右侧 `.oa-tags` 也会被盖。

### 修改
- `src/styles/global.css`
  - 新增共享的 `.mg-toolbar` 基础规则（原来只定义在 `DashboardManagement.css`，且仅 DashboardManagement/PluginManagement/DeployPage 三处复用、依赖加载顺序，不可靠），`padding` 右内边距预留 `180px`（`14px 180px 14px 24px`），给浮层让位。
  - `.oa-head` 右内边距也预留 `180px`（`0 180px 0 12px`）。
  - 注意：未动通用 `.toolbar`（仅编辑器窗口 `Toolbar.tsx` 使用，那里没有 UserMenu 浮层，不应缩进）。
- `src/management/DashboardManagement.css`：删除原 `.mg-toolbar` 重复定义（基础规则已上移 global.css），避免被后加载的页面 CSS 覆盖、重新引发遮挡。响应式 `@media(max-width:560px)` 里的 `.mg-toolbar` 覆写保留（移动端工具条换行，属已知边缘情况）。
- `src/auth/UserMenu.tsx`：容器加 `maxWidth:160; overflow:hidden`，用户名 `span` 加 `maxWidth:72; ellipsis; nowrap`，确保长用户名也不会撑破预留宽度。
